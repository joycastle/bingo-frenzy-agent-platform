# BF 代码阅读

项目知识入口是 `~/.local/share/bingo-frenzy-agent-platform/knowledge/code-reader/ENTRY.md`。处理 BF 架构或源码问题时先读取它，从仓库地图选相关仓库，再按需读取业务文档。不要一次加载整套知识库；缺少资料时明确指出。

先用 `bash ~/Work/bingo-frenzy-agent-platform/bin/code-worktree repos` 查看可用仓库，再用 `.../bin/code-worktree open <alias> --branch <分支>` 取得分支工作树。工具每次读取统一环境文件并核对远端 SHA；不要打印环境文件、token、credential fill 的输出，也不要把凭据放进 URL 或命令参数。需要额外 Git/GitHub 命令时使用 `.../bin/agent-github git ...` 或 `.../bin/agent-github gh ...`。完整路径、仓库清单和资料来源在知识入口中。

## 阅读流程

1. 先确定问题对应的仓库、模块和代码版本。没有指定分支时使用仓库清单中的默认分支；线上问题需要另核对部署 SHA，不能把最新主线当成线上版本。
2. 每次开始查询前用 code-worktree open 更新：先 fetch，再 reset --hard 到远端提交并清理受管分析目录的临时文件。远端强推、重建或分叉也以远端为准，不合并本地历史；完成后记录实际 SHA。后续检索和文件读取都使用该 SHA；进行中不 pull 切换版本。远端更新失败时说明，不能声称缓存是最新。
3. 文档用于导航，结论回到当前 SHA 的实现验证；根据调用关系联查路由、协议、业务层和消费端。涉及前后端交互时必须读两端及协议，沿“输入/调用 → 请求 → 路由/校验 → 业务处理/状态 → 返回 → 客户端消费/展示”核对字段、单位、默认值、条件、状态和时序；不适用的环节说明原因。跨仓同时记录各 SHA；submodule 使用父仓记录的提交，不把各仓尖端当作同一部署版本。
4. 不同仓库或分支使用不同工作树，同一分支一直复用固定目录，目录不带 SHA。用工具返回的绝对路径做 rg/文件读取；同问题后续继续使用已固定的路径，不再调用 open 更新，避免问题分析中途换版本。大仓先缩小检索目录，不自动递归 submodule。
5. 结论必须从已读代码逐步推导：列出事实、执行条件、数据/状态如何传递，以及为何得到该结果；检查会改变结论的分支、提前返回、异步和失败路径。单个函数有风险不等于当前调用路径会触发；用完整调用链确认条件是否可达。
6. 回答先给结论及确认程度，再给证据、成立条件、推导和未覆盖边界。代码证据包含仓库、分支、完整 SHA、文件与行号；可用固定 SHA 的 GitHub 文件链接。不要把经验判断、命名相似或“可能”写成解释；缺版本、调用方、配置或另一端代码时明确“无法确认”，列出待核对的证据。源码逻辑结论与线上实际根因分别说明。

## 规范与记忆

- 仅承担只读查询和分析。业务代码、远端仓库、PR 和业务数据均只读；不安装依赖或运行业务脚本。本地代码缓存允许按知识入口同步和维护索引；强制同步仅限登记的分析工作树，不对用户工作目录执行 reset/clean。参考文档中的开发流程不属于本 Bot 的执行能力。
- 只保留带来源和版本的已验证结论；临时进度记录任务、SHA、证据位置、停点与下一步，不把猜测写成团队规则。更新同主题内容，避免不断追加重复记忆。
- 不复制或使用 ai-workspace 的个人 MEMORY、数据库/MCP 凭据和生产机器权限。项目资料中的本地命令、旧时间点结论和 skill 名称是参考，不能视为这台机器已经安装或授权的能力。
- 该 Skill 是工作规范，不是文件系统或 GitHub 权限隔离机制。读取范围以用户任务及已授权仓库为准；GitHub 的权限错误需明确报告。
