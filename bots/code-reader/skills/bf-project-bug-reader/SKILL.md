# 飞书项目 Bug 阅读与分析

仅使用已连接的 `feishu-project` MCP 读取数据。当前个人账号在飞书项目 MCP 页面只开启查看权限；写工具即使出现在列表中，也不属于本 Bot 职责。不要发布评论、更新字段或流转状态。不得从报错切换身份或扩大权限。

## 读取顺序

1. `get_workitem_brief` 传用户提供的完整 `url`，`fields=["_all"]`。按返回的 `pagination` 读完字段；继续请求沿用返回的真实 `project_key`、工作项 ID 和 `next_page_token`。URL 中空间简称不等于真实 project_key，不猜测字段 key。
2. 提取标题、描述、环境、Build、版本、复现步骤、实际与预期结果、附件和关联需求。空白模板不等于没有 Bug，也不能据标题补写复现步骤。
3. `list_workitem_comments` 读取评论，按工具返回的分页信息继续读取；记录补充说明的时间。区分报告者描述、后续更正和已验证结论。
4. 读取关联需求：优先使用字段返回的关联 ID；必要时用 `list_related_workitem` / `list_workitem_relations`。需求若链接到飞书云文档，当前项目 MCP 不等于已有文档权限；没有文档工具时明确资料缺口。
5. 日志、截图和视频来自附件字段、评论或富文本。当前官方只读偏好允许读取附件列表，但实测 `get_download_url` 同样返回 `MCPPersonalPreferenceDisabled`；遇到这个限制时报告“附件元信息已读，内容未能读取”，不扩大权限、不换身份或借用浏览器登录绕过。若未来管理员另行授权下载，使用该工具取得签名计划并按返回的方式读取；URL 和签名视为私有数据，不在回答、公开仓库或普通日志中输出。文件留在当前 Bot 任务目录，不能放受管代码工作树。未实际打开视频或日志时不得声称看过。

## 结合代码查问题

- 使用 `bf-code-reader` 更新并读取必要仓库。环境映射按仓库区分：服务端线上 `master`、测试 `test`、策划测试 `design`；客户端线上 `master`、测试和开发 `develop`。客户端没有专门约定策划测试对应分支，需核对目标 Build 后再选。用户明确指定分支优先；环境和分支都没指定时用 `master`。
- Bug 单写明环境或 Build 就不是“用户未指定环境”。不能忽略 Test 字段直接查询线上默认分支，也不能把分支 tip 当该 Build 或部署的实际版本。
- 依照描述和附件中的输入、版本、状态、调用顺序核对前后端及协议。用户反馈是待验证现象，评论中的解释也要回到需求和代码核对。
- 输出：已确认结论及范围 → Bug/需求来源 → 仓库、分支、SHA、文件行号与推导 → 证据缺口 → 可执行的复现/验证步骤。证据不足明确无法确认，不凭相似问题猜根因。
- 工具调用检查 `isError` 和结果正文；HTTP/MCP 连通成功不等于业务读取成功。权限错误如实报告，不请求用户贴 Token，不输出环境文件或身份凭据。
